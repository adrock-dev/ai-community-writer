# 글 생성 프롬프트 안내

글 한 편이 어떤 재료로 조립돼 LLM에 넘어가고, **무엇을 고치면 글이 달라지는지**를 설명한다.
프롬프트를 바꾸려는 사람이 가장 먼저 읽을 문서다.

## 이 문서의 자리

`docs/content-generation/`(100건 넘는 문서)와 혼동하지 말 것. **그 폴더는 기록이다** —
README가 "현행 문서가 아니다"라고 명시하고 있고, 대부분 폐기된 T01 시절의 실험 계획·측정
결과다. 그 폴더를 근거로 코드를 고치면 지금 도는 글에는 아무 효과가 없다.

이 문서는 **지금 도는 것**을 설명한다. 다만 프롬프트 문장 자체는 옮겨 적지 않는다 —
문장의 정본은 코드이고, 여기 복사하면 두 곳이 같이 썩는다. 이 문서가 답하는 것은
"어느 층이 무엇을 정하고, 그 층은 누가 소유하는가"다.

---

## 1. 글 한 편이 만들어지는 경로

```
슬롯 하나 선택
  → 사실 재료(facts) 조립      학원·지역·후기·이미지를 DB에서 모은다
  → 프롬프트 조립(buildPrompt)  아래 §2 의 층들을 쌓는다
  → LLM 호출(runLlm)           codex 또는 claude CLI 서브프로세스
  → 품질 게이트                 완성된 글을 규칙으로 검사한다
  → (이슈 있으면) 재작성 요청    게이트가 잡은 것만 고치라고 다시 시킨다
  → 통과: posts 에 발행 / 실패: draft_posts 에 격리
```

**중요한 성질 셋.**

- **LLM 호출은 본문 생성 하나뿐이다.** 제목 전용 호출도, 섹션 계획 호출도, 생성 시점 웹 검색도 없다.
  제목은 규칙(`TITLE_RULES`)이 생성 시점에 확정해 프롬프트에 못 박는다.
- **재작성은 무한하지 않다.** 횟수는 잡 payload가 정하고 상한이 있다. 다 쓰고도 통과하지 못하면
  버리지 않고 격리한다.
- **게이트는 프롬프트 밖에 있다.** 프롬프트로 달래는 것과 게이트가 막는 것은 다른 층이다(§5).

---

## 2. 프롬프트의 층 — 누가 무엇을 소유하는가

프롬프트는 아래 순서로 쌓인다. **고칠 곳을 찾을 때는 "그 문장이 어느 층인가"부터 판단한다.**

| 층 | 무엇을 정하나 | 소유자 | 운영자가 화면에서 바꿀 수 있나 |
| --- | --- | --- | --- |
| 역할 문장 | "한국어 SEO 블로그 에디터다" | `worker.service.ts#buildPrompt` | ✗ |
| 브랜드·업종 | 글에 나가는 이름 | 도메인 설정(DB) | ✓ 도메인 관리 › 설정 |
| 디자인 지침 | 섹션 배치·강조·CTA 톤 | `constants.ts`의 디자인 템플릿 | ✓ 글유형/디자인 |
| **지침 우선순위** | 층이 충돌할 때 무엇이 이기나 | `buildPrompt` | ✗ |
| 템플릿 필수 구조 | H2 구성·표·이미지 배치 | `archetypes.ts`(아키타입) | ✗ |
| 원본 기반 작성법 | 실제 상위 노출 글의 서술 방식 | `archetypes.ts`의 `writing_guide` | ✗ |
| 원본 전체 글 패턴 | 21,275개 글에서 뽑은 제목·헤딩 패턴 | `data/content_research/…` (JSON) | ✗ |
| 슬롯 축 | 주 키워드·지역·페르소나·의도·수식어 | 슬롯 + 글유형 `axis_values` | ✓ 글유형/디자인 |
| **공통원칙** | 이 사이트만의 말투·태도 | 도메인 `common_principles`(DB) | ✓ 글 공통 설정 |
| **글유형 방향성** | 그 글유형의 각도·전개·격식 | 글유형 `direction`(DB) | ✓ 글유형/디자인 |
| 확인된 콘텐츠 재료 | 학원·후기·이미지 등 사실 | `buildFacts` → DB | 간접(원천 데이터·연결) |
| **절대 원칙** | 날조 금지·내부 흔적 금지 등 | `constants.ts` 상수 | ✗ |
| 학원 원칙 | 후보 수·지역 일치·수강료 단서 | `constants.ts` 상수 | ✗ |
| 필수 출력 구조 | 첫 줄 H1·제목 고정 등 | `buildPrompt` | ✗ |
| 문체/분량 | 길이 하한·상한, 톤 | `buildPrompt` + 아키타입 | ✗ |

**층 사이의 우선순위는 프롬프트가 명시한다** — 글유형·검색 의도·검증된 재료가 상위 계약이고,
디자인 지침은 보조다. 충돌하면 글유형이 이긴다.

### 글유형별 계약은 따로 있다

지금 도는 학원 글은 전부 **T16(`local_axis`)**이고, T16 전용 계약·문체는 `t16-axis-comparison.ts`가
소유한다. 축(persona/intent/modifier)이 요약표 열·강조 섹션·제목 부제를 실제로 결정하는 것도 여기다.
`t01-*.ts`는 **폐기된 계열**이라 고쳐도 지금 글에 영향이 없다.

## 3. 무엇을 고치면 글이 달라지나 — 증상별

| 하고 싶은 것 | 고칠 곳 |
| --- | --- |
| 말투·격식을 바꾸고 싶다 | **글유형 방향성**(화면). 격식은 방향성이 최종 결정권을 갖는다 |
| 이 사이트 전체의 태도를 바꾸고 싶다 | **공통원칙**(화면). 단 §4의 경고를 먼저 읽을 것 |
| 섹션 순서·H2 구성을 바꾸고 싶다 | `archetypes.ts` — 글유형이 아니라 **아키타입**이 구조를 소유한다 |
| 학원 카드의 불릿·인용 위치를 바꾸고 싶다 | `buildPrompt`의 학원 카드 지침 + `t16-axis-comparison.ts` |
| 요약표 열을 바꾸고 싶다 | `t16-axis-comparison.ts`(축이 열을 정한다) |
| 제목 형식을 바꾸고 싶다 | `constants.ts`의 `TITLE_RULES` — LLM이 아니라 규칙이 정한다 |
| 날조·과장을 더 강하게 막고 싶다 | **프롬프트가 아니라 품질 게이트**(§5) |
| 글에 쓰이는 사실을 늘리고 싶다 | 프롬프트가 아니라 **재료** — 원천 데이터 동기화 → 학원자료 연결 |
| 특정 문구를 못 쓰게 하고 싶다 | 도메인 **제외어**(화면). 판박이 문장은 **감시 문구**로 재작성을 유도 |

---

## 4. 고칠 때의 함정

- **공통원칙은 어떤 게이트도 검증하지 않는다.** 프롬프트에 들어가기만 한다. 여기에 「절대 원칙」이나
  아키타입 지침이 이미 강제하는 내용을 다시 적으면 **강제력은 안 생기고** 여기서만 전달되는
  톤·태도 지시만 희석된다. 화면 안내도 그렇게 말한다.
- **T01 계열을 고치면 아무 일도 일어나지 않는다.** 학원 글의 정본은 T16이다. 고칠 곳은
  `t16-axis-comparison.ts`와 `archetypes.ts`의 `local_axis`다.
- **프롬프트 지시에는 강제력이 없다.** 근거로 쓸 수 없는 자료는 "쓰지 말라"고 적는 대신
  **입력에서 끊는다.** 블로그 리뷰가 그렇게 처리됐다(수집 스위치와 별개로 프롬프트에서 하드 오프).
- **LLM 래퍼가 둘이다.** 글 생성·축 제안은 `llm-runner.ts`, 학원 심층조사는 `academy-research-llm.ts`가
  각자 spawn·파서를 갖는다. 한쪽만 고치면 다른 쪽은 조용히 옛 동작을 유지한다.
- **생성에는 로컬 CLI 인증이 필요하다.** API 키가 아니라 `codex`/`claude` 서브프로세스를 쓴다.
  인증이 없으면 프롬프트가 아무리 옳아도 생성 자체가 실패한다.

## 5. 프롬프트로 고칠 수 없는 것 — 품질 게이트

게이트는 **완성된 글을 규칙으로 검사**한다. 프롬프트가 아무리 잘 지시해도 결과가 규칙을 어기면
막힌다. 반대로 게이트가 검사하지 않는 것은 프롬프트가 아무리 강하게 적어도 새어 나갈 수 있다.

게이트가 보는 것(대표): H1 존재·본문 길이·H2 구조·표/목록/FAQ 같은 구조·내부 API 흔적 노출·
위험한 과장·이미지 슬롯 사용·실제 후보 수보다 부풀린 숫자·제외어.

**게이트를 고칠 때는 반드시 두 곳을 함께 고친다** — 런타임 게이트(`quality-gate.ts`)와
렌더 인식 게이트(`scripts/qa-posts.mjs`)가 로직을 공유하지만 DRY하지 않다. 어긋나면
드리프트 가드 테스트(`test/gate-parity.test.ts`)가 실패한다. 마크다운 렌더러도 같은 이유로
양쪽에 복제돼 있다. 이 대조가 없던 시절 같은 렌더 버그가 양쪽에 남아 **게이트가 자기 버그를
통과시킨** 적이 있다.

책임 분담의 원칙은 이렇다.

- **사실이 맞는가** → 재료(입력)에서 끊는다. 프롬프트로 달래지 않는다.
- **형식·구조가 맞는가** → 게이트가 막는다.
- **어떤 각도로 어떻게 말하는가** → 프롬프트(방향성·공통원칙)가 정한다.

---

## 6. 직접 확인하는 법

프롬프트는 조건 분기가 많아 **코드만 읽어서는 실제로 무엇이 들어갔는지 알기 어렵다.**
`apps/api-nest/src/scripts/`에 실제 프롬프트를 덤프하고 게이트를 단독으로 돌려 보는
스크립트들이 있다(`dump-t01-prompt.ts`, `gate-check-file.ts`, `run-prompt-file.ts` 등).
**프롬프트를 고치기 전에 지금 값을 한 번 덤프해 두고, 고친 뒤 다시 떠서 비교하는 것을 권한다.**

생성 결과를 실제로 확인하려면 관리자 화면에서 **1개 테스트 작성** → **글 상세의 「이 글의 근거」**를
본다. 그 글이 학원·후기·이미지를 얼마나 썼는지, 못 쓴 값이 무엇인지 보여준다.
